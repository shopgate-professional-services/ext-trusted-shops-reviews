## Project Overview

Shopgate Connect app extension that replaces the app's own product reviews and
rating stars with Trusted Shops (eTrusted) data. Frontend portal components swap
the review sections of the theme for the original `<etrusted-widget>`, and a
backend step overwrites `product.rating` in the catalog pipelines so that every
place the theme draws stars follows along. Everything is driven by merchant
configuration; no merchant-specific values live here.

## Tech Stack

Two independent npm packages with no root `package.json`. They do not share tooling.

- `extension/` — backend pipeline step. CommonJS, **no runtime dependencies**: the
  eTrusted feeds are read with the built-in `https` module. Lint via `eslint` 8 with
  `eslint-config-standard`, tests via mocha.
- `frontend/` — React 17 portal, widget and subscriber components. ES modules and JSX,
  `react-redux` 8, `@shopgate/engage` 7.31. Lint via `eslint` 8 with
  `@shopgate/eslint-config`, tests via jest from `@shopgate/pwa-unit-test`.

## Common Commands

Run these from inside one of the two package directories — there is no root package.

Backend (`extension/`):

```
npm install
npm test           # mocha --recursive test/unit
npm run lint       # eslint --ext .js .
```

Frontend (`frontend/`):

```
npm install
npm test           # jest, config re-exported from @shopgate/pwa-unit-test
npm run lint       # eslint, uses the root .gitignore as its ignore file
```

Neither half has a build step; the theme builds the frontend. The repository does
not document how to run the extension against a shop — verify the platform SDK
workflow elsewhere before relying on it.

## Repository Structure

- `extension-config.json` is the wiring. `components[].path` points at a single
  component file, `steps[].path` at the one backend step plus the pipeline hooks it
  attaches to. Nothing in this repository reads that manifest — the platform tooling does.
- Backend entry point is `extension/overrideProductRating.js`,
  `async (context, input) => ({ products })`. `extension/lib/` holds the parts it uses:
  `identifier.js` (which product field, and the hex encoding a SKU needs in the feed URL),
  `grades.js` (feed access, cache, time budget), `baseProducts.js` (the learned
  variant → main product memory), `storage.js` (shared eviction helper).
- `frontend/settings.js` is the single place the admin configuration enters the frontend;
  `frontend/constants.js` holds the class names and DOM selectors that both the components
  and outside styling rely on.
- `frontend/components/EtrustedWidget` builds the custom element; both portals that show
  reviews render through it.
- Reading order: `extension/overrideProductRating.js` → `lib/grades.js` →
  `lib/baseProducts.js`; frontend `settings.js` → a portal.

## Local Development Notes

- `extension/config.json` and `frontend/config.json` are generated by the platform tooling
  from the manifest `configuration` block. Both are gitignored and absent from a fresh
  checkout. The two halves read their configuration differently: `frontend/settings.js`
  imports its copy as a default import at module load, so the frontend cannot be linted or
  tested against a fresh checkout, while the backend step takes everything from
  `context.config` and never touches the generated file.
- No lockfiles are committed, so installs are unpinned.
- Product reviews have to stay switched on for the app (`hasReviews`). With that setting
  off the theme renders no star slots at all and there is nothing for this extension to
  attach to.

## Testing Notes

- Backend: mocha, files at `extension/test/unit/<subject>.spec.js`.
- Frontend: jest, co-located `spec.js` / `spec.jsx`. `frontend/jest.config.js` is a one-line
  re-export of `@shopgate/pwa-unit-test/jest.config`.
- Specs that need a different generated config load the component through a helper that
  calls `jest.resetModules()` and mocks `../../config.json` virtually. That trick only works
  with a shallow render — in a spec that mounts, the reset produces a second React instance
  and every hook call fails. `portals/ListRatingValue/spec.jsx` therefore mocks
  `../../settings` instead.
- `ListRatingValue` measures real geometry. jsdom reports zeros for
  `getBoundingClientRect` and empty strings for computed styles, so its specs stub both.

## Deployment / CI Notes

There is no CI configuration in this repository — no workflow, pipeline or Docker files.
Both halves have to be linted and tested by hand before a pull request.

## Project-Specific Pitfalls

- `rating.average` is on a 0–100 scale in the theme. The backend multiplies the 0–5 value of
  the feed by `RATING_SCALE_FACTOR = 20`, the frontend divides by `RATING_SCALE_DIVISOR` again
  for display. Getting this wrong yields five full stars everywhere.
- An unknown eTrusted channel answers with HTTP 200 and `{}`, which is indistinguishable from
  "no reviews yet". The step therefore trusts a channel only once it has seen at least one
  rating from it and otherwise leaves the ratings of the shop untouched.
- Only `getProductsByIds.v1` and `getProductsByCategory.v1` carry the hook.
  `getProduct.v1` delegates to ByIds, so hooking it as well runs the step twice over the same
  products; `getProducts.v1` has no `afterFetchProducts` hook at all.
- The step must never throw and must always return a `products` array — a failing rating
  lookup may not cost the shop its catalog.
- `PipelineRequest` is frontend-only and cannot be used inside a step.
- Product cards, grids and sliders draw their stars without a portal around them. That is why
  the values are replaced in the backend, and why `ListRatingValue` places an anchor element
  into the stars element of the theme by hand instead of rendering into a portal.
- Card geometry is measured, never assumed: `ListRatingValue` moves its row out from under
  anything that hangs into it and drops the count, then the value, when the card is too narrow.
  A fixed pixel value breaks as soon as another extension moves the favourites button —
  `ext-product-list-add-to-cart` overrides the same `product-item.favorites-button` portal.
- The extension `id` carries no `ext-` prefix (`@shopgate-project/trusted-shops-reviews`);
  only the repository is named `ext-…`. Keep `name` in both `package.json` files identical to it.
- The version is stated three times — `extension-config.json`, `extension/package.json` and
  `frontend/package.json`. Keep them in sync.
- `CHANGELOG.md` documents released versions only; beta iterations get no entry of their own.

## Editing Guidelines for AI Agents

- Never commit `extension/config.json` or `frontend/config.json`; both are generated.
- Import the generated frontend config as a **default** import including the `.json` extension.
  Do not silence the resulting `import/no-unresolved` with an `eslint-disable` comment: once the
  extension has been attached once the import resolves and the directive itself becomes the error.
- Reuse what the platform already offers before writing your own — `RatingStars`,
  `VisuallyHidden`, `getProductDataById` from `@shopgate/engage/product/selectors/product`.
- Connect components with `useSelector` / `useDispatch` inside the component. No `connector.js`
  plus `connect()` HOC.
- Styles come from `makeStyles()`; never put comments inside a style object.
- Backend logging goes through `context.log`, never `console.log`.
- The two halves use different linters with different style rules. Match the half you are
  editing; do not restyle the other one.
